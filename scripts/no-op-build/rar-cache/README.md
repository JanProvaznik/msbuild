# Observed RAR result-cache experiment

This is an **opt-in task implementation**, not the earlier coarse target skip.
It replaces only `Microsoft.Build.Tasks.Core.dll` in a private SDK copy. It
does not replace the engine, skip SDK targets, suppress hooks, disable
SourceLink, or require building the whole dotnet repository.

The question being tested is narrower than "can we make the entire build a
no-op?": **can RAR validate what it observed and replay its complete result,
without resolving the assembly graph again?** Yes, for the supported contract
below. Whether that saves wall time depends on how much resolution was actually
being performed. See the [investigation](../../../documentation/investigations/rar-result-cache.md)
and `results` for both improvements and regressions.

## Source and build

`source.patch` applies at the root of the exact SDK's **dotnet/dotnet** checkout,
commit `14fbf8d5271c98133561eb55185fdb05b286f578`. It includes the RAR implementation,
parameter helpers, project inclusion, localized resource entries and focused
regression tests. It does not include the earlier SDK target patches.

From that VMR checkout:

```powershell
git apply --check <experiment>\source.patch
git apply <experiment>\source.patch
Set-Location src\msbuild
dotnet msbuild src\Tasks\Microsoft.Build.Tasks.csproj -t:Restore -v:q -nologo
dotnet msbuild src\Tasks\Microsoft.Build.Tasks.csproj -v:q -nologo `
    -p:TargetFramework=net10.0 -p:Configuration=Release
```

Restore all project frameworks; do not force `TargetFrameworks=net10.0` during
restore because some project references build `netstandard2.0`.
The checkout uses SDK 10.0.300 to build this task. Execution uses SDK 10.0.400.
Do not edit either checkout's `global.json` or installed SDK files.

From this MSBuild experiment branch:

```powershell
.\scripts\no-op-build\rar-cache\New-RarCacheSdk.ps1 `
    -MSBuildSource <vmr>\src\msbuild -OutputDirectory <artifacts>\rar-sdk
```

The resulting SDK is `<artifacts>\rar-sdk\sdk\10.0.400`. Keep this version-shaped
directory: workload resolution expects a valid SDK version in its path.
The script adds the optional RAR input to the existing task invocation and
registers the `.results` file in `FileWrites`, including the off/on control arm.

Run using that host:

```powershell
$sdk = '<artifacts>\rar-sdk\sdk\10.0.400'
$env:DOTNET_HOST_PATH = 'C:\Program Files\dotnet\dotnet.exe'
$env:MSBuildSDKsPath = "$sdk\Sdks"
& $env:DOTNET_HOST_PATH "$sdk\MSBuild.dll" <project-or-solution> `
    -nologo -v:q -m:8 '-p:NetCoreRoot=C:\Program Files\dotnet\' `
    -p:EnableRARResultsCache=true
```

Restore the workload separately first. `EnableRARResultsCache=false` is the
rollback; it executes the ordinary RAR implementation. The task's direct API
is `EnableResultsCache`; its diagnostic output is `ResultsCacheHit`.
The default remains off. This is a research patch, not a recommendation to
enable caching on all projects.

For the measurements, build the small existing probe/logger:

$env:DOTNET_HOST_PATH = 'C:\Program Files\dotnet\dotnet.exe'

## Reproduce the evidence

| Script | Purpose |
| --- | --- |
| `Test-RarCache.ps1 -SdkDirectory $sdk -OutputRoot <fresh-directory>` | Real builds, reference-output metadata parity, positive/negative invalidation, diagnostics, corruption and hooks |
| `Test-RarMetadata.ps1 -SdkDirectory $sdk -AssemblyPath <physical-v1-dll> -OutputRoot <fresh-directory>` | Disk v1 / synthetic framework v2 / disk v1 / cached synthetic v2 in one MSBuild process |
| `Measure-RarCache.ps1 -SdkDirectory $sdk -Root <workload-root> -Project <entry> -OutputDirectory <fresh-directory>` | Five alternating off/on pairs, per-sample hit/miss counts, separate diagnostic binlogs |
| `Measure-RarMatrix.ps1 -Registry <registry.json> -SdkDirectory $sdk -OutputRoot <fresh-directory>` | Nine earlier solution fixtures, three pairs each, all `bin` output paths and hashes compared |
| `Measure-RarTask.ps1 -SdkDirectory $sdk -Assemblies <dll-paths> -SearchDirectories <directories> -OutputRoot <fresh-directory>` | Twenty repeated real assembly-closure resolutions per arm; task microbenchmark, not a whole-build speedup |
| `New-FileReferenceScenario.ps1 -OrchardAssembly <OrchardCore.ContentManagement.dll> -OutputRoot <fresh-directory>` | Eleven-project solution with ten ordinary file references to an actual Orchard assembly |

The nine-solution registry is generated by
`..\roadmap\scenarios\Setup-ScenarioMatrix.ps1`. Existing restored fixtures can
be reused. Keep result directories outside workload roots; otherwise globs can
observe the experiment's logs. `AdditionalArguments` on `Measure-RarCache.ps1`
can select other supported build scenarios without changing the workload.

For the file-reference solution, restore/build its `Scenario.slnx`, execute
`App\bin\Debug\net10.0\App.dll`, and compare stdout with `scenario.json`'s
`expected` value before and after the experiment. This fixture uses file
references deliberately; it must not be described as Orchard's normal
PackageReference/project-reference build.

Timed calls use the same lightweight `RarCacheLogger` in both arms, not a binary
logger. The final runner records hit/miss/bypass counts and cumulative RAR task
milliseconds. The logger retains only cache-status messages and task timings;
it does not request item/parameter payloads. Three **additional**, untimed
binlogs capture cache fill, cache hit and control. Logging changes RAR's
observable message policy, so each policy needs its own cache population.
Do not compare logged and unlogged wall times as if they were the same run.
Earlier intermediate CSVs predate some of these counters; their headers show
which evidence was actually collected.

## Supported freshness contract

- The task hashes all declared input values, ordered item arrays, escaped custom
  metadata, defining-project information, task-local environment, relevant
  host/logging settings and task/framework/utility module versions. A private
  legacy empty-App.config flag is included because its public getter loses that
  distinction.
- It observes actual file probes, including rejected and nonexistent candidates,
  timestamps consumed by assembly-metadata readers, directory existence and
  directory enumeration. New XML/PDB files, higher-priority assemblies, culture
  directories and changed transitive assemblies can invalidate the result.
- Ordinary files use existence/UTC last-write time/length/attributes. **This is
  a timestamp contract, not content-addressed PE validation.** Replacing a PE
  while preserving those fields is outside the contract. App.config is content
  hashed because RAR parses that semantic input afresh.
- Directory batching compares only observed filenames and their metadata. It
  does not assume that an unchanged directory timestamp proves all child files
  unchanged.
- Recorded inputs are rechecked after computation before storing. This does not
  make builds transactional against concurrent filesystem mutation.
- Full-framework/redist/profile tables, framework directories, SDK-reference
  tables, GAC/registry/AssemblyFolders and unknown resolver macros fall back.
  So do out-of-process RAR, custom cultures and `FailIfNotIncremental`.
  The .NET Framework task build retains ordinary execution.
- Warnings, errors and unsupported event types decline storage. A warning is
  never replaced by a successful cached result, including `WarnAsError`.
  Successful ordinary information messages are replayed under the current task.
- All output item arrays, order, metadata, booleans, copy-local items and
  `FilesWritten` are restored. Replayed items are separate mutable instances.
  Metadata deltas share verified input metadata rather than serializing the same
  SDK metadata repeatedly. `OriginalItemSpec` and `RecursiveDir` are retained.
- The legacy metadata cache is not a semantic input: ordinary RAR can rewrite
  it without changing resolution. Its existence is nevertheless required if
  replayed `FilesWritten` promises it; deletion forces normal recreation.
- Disk-derived metadata and synthetic framework identity must have separate
  provenance. A miss uses real file generations and applies task-supplied
  synthetic name/runtime overrides outside disk-metadata cache delegates.

Entries are Brotli-compressed, have whole-entry SHA-256 integrity, a bounded
decompressed size, versioned framing and atomic replacement. Corrupt or
unreadable cache files fall back. Writes and cleanup failures are reported at
low importance rather than failing a previously successful resolution.
Cache files are intermediate build artifacts, not an authenticity/security
boundary.

## Remaining rollout gates

No default enablement is proposed. Missing gates include Linux/macOS execution,
cross-process/concurrent-mutation stress, design-time builds, supported expansion
of full-framework/GAC/redist resolution, RID/self-contained/AOT/signing, and a
separate pass over publish/pack protocols with this task implementation.
The previous target-only publish/pack evidence does not certify this new cache.
Most importantly, a high hit rate alone is **not** evidence of a whole-build win.
