# Native MSBuild incrementality experiment

> **Laboratory only, not a general SDK optimization.** The
> [red-team roadmap](../../../documentation/specs/proposed/target-incrementality-roadmap.md)
> reproduced seven incompatibilities in the original boundary. Known cases
> have been mitigated, but arbitrary hook/state contracts remain unsupported.
> Use the [safe-tier harness](../roadmap/README.md) for compatibility-preserving
> comparisons. Historical 7.59/6.18-second numbers below are not a blanket
> correctness claim.

This is the follow-up to the external freshness-gate experiment. **These builds
run ordinary `dotnet build` and use native MSBuild targets throughout.** There
is no watcher, filesystem snapshot service, replacement build host, or cached
project-instance replay.

The experimental targets use built-in `Inputs`/`Outputs`, `CallTarget`, `Hash`,
`WriteLinesToFile`, `ReadLinesFromFile`, and `Touch`. They do create ordinary
per-project `obj` cache/stamp files: an input-list/configuration hash, a list of
actual generated outputs, and a completion stamp. The translation leaf has its
own execution-time mapping cache and completion stamp. This is target-level
incrementality, not statelessness.

On the pinned 202-project OrchardCore CMS workload, five paired samples gave:

| Same SDK and hosting mode | Stock | Native targets |
| --- | ---: | ---: |
| MSBuild server off | 20.47 s | 7.59 s |
| MSBuild server on | 17.24 s | 6.18 s |
| Tasks | 23,697 | 7,857 |
| RAR invocations | 202 | 0 |
| Copy invocations | 3,393 | 0 |

Both versions already had zero compiler invocations. Native targets avoid much
of the preparation needed to arrive at that decision.

## Try with the installed SDK first

Use the already-restored/built workload from the
[parent laboratory instructions](../README.md). From this MSBuild checkout:

```powershell
$inject = (Resolve-Path .\scripts\no-op-build\native\inject.targets).Path
Push-Location C:\lab\OrchardCore
dotnet build src\OrchardCore.Cms.Web\OrchardCore.Cms.Web.csproj --no-restore -m:8 -v:q `
    "-p:CustomAfterMicrosoftCommonTargets=$inject" `
    -p:NativeCoreBuild=true -p:NativeCoreBuildContract=DeclaredInputsAndHooksV1 `
    -p:NativeIncrementalTranslations=true
Pop-Location
```

Warm the exact import configuration before measuring. Adding or editing a
targets file legitimately invalidates compilation. This version leaves the
SDK's empty framework-pack tasks unchanged; it needs no SDK copy.

## Complete SDK-target experiment

The remaining SDK hotpatch adds empty-input conditions to ten
`GetPackageDirectory` task sites. It never changes the installed SDK.

```powershell
.\scripts\no-op-build\native\New-PrivateSdk.ps1 `
    -Sdk 'C:\Program Files\dotnet\sdk\10.0.400' `
    -OutputDirectory C:\lab\native-sdk

.\scripts\no-op-build\native\Measure-Native.ps1 `
    -Root C:\lab\OrchardCore `
    -Project src\OrchardCore.Cms.Web\OrchardCore.Cms.Web.csproj `
    -PrivateSdk C:\lab\native-sdk `
    -OutputDirectory C:\lab\native-measurements `
    -Iterations 5 -IncludeServer -AcknowledgeExperimentalCoreContract
```

Use fresh SDK/output directories. Copying the whole SDK directory is intentional:
SDK targets import sibling Roslyn, NuGet pack targets, bundled-version props,
and RID graphs. Copying only `Sdks` silently loses necessary imports.
No dotnet sources are built, and installed runtimes/targeting packs are reused.

The measurement script warms configurations, alternates stock/native builds,
stores every elapsed sample, and captures separate binlogs. The control uses
the same private SDK and a dormant import, with all three feature flags false.
The dormant import keeps `IncrementalClean` from deleting the experiment's
cache files during control runs. This prevents an artificial cache miss on
each subsequent native sample.

For a single invocation, the configuration generated by `New-PrivateSdk.ps1`
supplies the two relevant paths:

```powershell
$config = Get-Content C:\lab\native-sdk\configuration.json -Raw | ConvertFrom-Json
$inject = (Resolve-Path .\scripts\no-op-build\native\inject.targets).Path
$oldSdkPath = $env:MSBuildSDKsPath
try
{
    $env:MSBuildSDKsPath = $config.MSBuildSDKsPath
    Push-Location C:\lab\OrchardCore
    dotnet build src\OrchardCore.Cms.Web\OrchardCore.Cms.Web.csproj --no-restore -m:8 -v:q `
        "-p:NetCoreRoot=$($config.NetCoreRoot)" `
        "-p:CustomAfterMicrosoftCommonTargets=$inject" `
        -p:NativeCoreBuild=true -p:NativeCoreBuildContract=DeclaredInputsAndHooksV1 `
        -p:NativeIncrementalTranslations=true `
        -p:NativeSkipEmptyFrameworkPacks=true
}
finally
{
    Pop-Location
    $env:MSBuildSDKsPath = $oldSdkPath
}
```

Add `-bl:C:\lab\native.binlog` to observe the skipped targets. Do not include
logging in only one side of a timing comparison.

## What changed

`core-products.targets` moves the original `CoreBuildDependsOn` chain inside an
incremental target body. `CallTarget` runs that chain only when MSBuild's
timestamp check says the products are stale. Project references are still
built first. `GetTargetPath` and ordinary `BeforeBuild`/`AfterBuild` entry points
remain available outside the skipped products target.

The early check accounts for source/resource/content input sets, selected
compiler/SDK settings, resolved package/framework files, known products and
missing outputs. `NativeCoreCompletion` metadata on existing project-reference
results propagates content-only changes even when a dependency's reference
assembly is unchanged. Non-participating references force the ordinary payload.

The translation target uses a native completion boundary and a single batched
Copy when dirty. The current mapping is hashed during leaf execution, after the public target's
BeforeTargets hooks; package downgrades and execution-time items therefore do
not disappear behind older source timestamps.
Destination timestamps and missing destinations also invalidate the leaf.
Its stamp is explicitly excluded from the core's products, avoiding a
core-stamp/translation-stamp feedback loop. Removed translation sources retain
old destinations, matching the original target's policy.

## Contract and limits

This is an **audited-workload proof of concept**, not a general SDK default.
It demonstrates a substantial leverage point in target authoring without an
engine change. It does not prove that arbitrary `CoreBuild` authoring is pure.

- The measured contract is ordinary local C# Build on .NETCoreApp/.NETStandard
  projects. The pinned SDK is 10.0.400 and the workload revision is recorded in
  the report. Do not assume compatibility with other SDK target definitions.
- Design-time/IDE builds, CI, SourceLink-enabled builds, `NoBuild`, compiler
  command-line-only modes, and nonempty pre/post-build commands retain the stock
  pipeline. `NativeForceCoreBuild=true` also selects the stock pipeline.
- Do not use this as an optimization for Publish/Pack or other target protocols
  without auditing their item/property contracts. Clean and build-after-clean
  are exercised by the fixture.
- A custom task inside the skipped payload with required per-invocation effects,
  undeclared environment/network/registry/clock inputs, or in-memory results
  needed elsewhere must opt out or be refactored into a declared boundary.
- The input signature covers the tested compiler/SDK configuration surface,
  not every arbitrary custom property or every SDK option. Extend
  `NativeAdditionalInputs`, `NativeAdditionalInputSignature`,
  `NativeAdditionalOutputs`, and `NativeNonCoreProducts` for audited extensions;
  otherwise leave `NativeCoreBuild=false`.
- Like ordinary MSBuild incremental targets, this assumes quiescent files and
  meaningful timestamps. In-place edits with preserved/backdated timestamps
  are not generally detected. The translation package-mapping downgrade case
  is specifically handled, not every possible mutation of a package cache.
- Generated outputs should not accidentally enter default input globs. The
  translation fixture explicitly excludes its `Localization` output directory.

The output-list cache is necessary because the SDK's existing FileWrites list
is a **superset of possible files**, including optional files never created.
Treating every FileWrites entry as a required output makes native targets
permanently dirty. Actual existing products are recorded only after successful
payload execution. Missing recorded products force work; a failure invalidates
the completion stamp. FileWrites registration and clean hooks cover the native
state files.

## Focused executable checks

```powershell
.\scripts\no-op-build\native\Validate-Contract.ps1 `
    -ArtifactsDirectory C:\lab\native-contract
.\scripts\no-op-build\native\Validate-Translations.ps1 `
    -ArtifactsDirectory C:\lab\native-translations
```

The scripts create fresh, isolated fixtures, compile/run their outputs, and
retain binlogs and JSON results. They cover method-body versus reference-API
changes, transitive content, source add/remove, missing outputs, compiler and
runtime-output properties, failures/recovery, clean, NoBuild/CI fallback,
non-participating project references, package downgrades, newer corrupted
translation destinations, and deleted destinations.

See the [native investigation](../../../documentation/investigations/native-target-incrementality.md)
and the committed [raw measurements](results/measurements.csv).
